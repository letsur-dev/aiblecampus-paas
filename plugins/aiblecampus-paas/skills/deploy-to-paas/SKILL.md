# 에이블캠퍼스 PaaS 앱 완성과 배포

사용자가 인프라를 이해하지 않아도 요청한 웹앱을 완성하고 접속 가능한 상태로 만든다. 소스 패키징, 컨테이너, revision과 내부 API는 작업 수단이지 사용자에게 설명할 기본 내용이 아니다.

## 기본 행동

- 사용자가 로컬에서만 작업해 달라고 하지 않았다면 구현과 검증 뒤 배포한다.
- 기존 프로젝트의 구조, package manager, lockfile과 실행 방식을 보존한다.
- 요청한 기능을 빠뜨리지 않고 완성한 뒤 `validate_project`를 통과한 정확한 소스만 배포한다.
- 사용자가 기존 배포를 수정하는 경우 같은 배포 이름을 사용해 접속 주소를 유지한다.
- 배포가 성공하면 URL과 사용 가능한 기능을 먼저 알려준다.
- 브라우저 조작, screenshot과 시각 검사는 사용자가 요청했거나 기능 확인에 꼭 필요한 경우에만 한다. 플랫폼 healthcheck 통과만으로 배포 완료를 판정할 수 있다.

## 사용자와 소통하는 방법

사용자는 비개발자일 수 있다. 진행 상황은 사용자가 이해할 수 있는 단계로 짧게 설명한다.

- 준비: "요청한 기능을 완성하고 있습니다."
- 검증: "완성된 앱이 정상적으로 실행되는지 확인하고 있습니다."
- 배포: "앱이 준비됐습니다. 지금 접속할 수 있게 배포하고 있습니다."

한 단계가 60초보다 오래 걸릴 때만 짧은 추가 진행 상황을 보낸다. 다음 내용은 사용자가 묻거나 직접 조치해야 할 때만 설명한다.

- 소스 압축과 업로드 방식
- 명령어, 파일 경로와 package manager 내부 처리
- 토큰, Credential, 내부 API 주소와 임시 파일
- 배포 ID, revision ID, 컨테이너, 이미지와 대기열 내부 수치

복구 가능한 기술 오류는 먼저 직접 해결한다. 실패한 명령과 긴 로그를 그대로 전달하지 말고, 해결할 수 없을 때만 사용자가 이해할 수 있는 원인과 필요한 다음 행동을 설명한다.

## 실행 경로 선택

### 빠른 배포 경로

다음 조건을 모두 만족하면 `validate_project`와 `deploy_project`만으로 진행한다.

- 프로젝트 구현이 이미 끝났다.
- 사용자가 기능 변경을 요청하지 않았다.
- 필요한 일반 설정과 비밀값이 준비돼 있다.
- DB나 파일 Storage가 필요하지 않다.
- 기존 검증 이후 소스가 바뀌지 않았거나 지금 다시 검증할 수 있다.

### 구현 및 복구 경로

다음 중 하나라도 해당하면 프로젝트를 먼저 점검하고 수정한다.

- 새 앱을 만들거나 기존 기능을 변경한다.
- 실행 명령, PORT, 환경변수 또는 Dockerfile 문제가 있다.
- 배포 전 검증이 실패한다.
- build, run 또는 health 단계에서 실패한다.
- 데이터 저장, 파일 업로드나 외부 서비스 연결이 필요하다.

중요한 제품 요구가 빠져 있고 안전하게 추론할 수 없을 때만 질문한다. 한 번에 최대 세 가지를 묻고, 나머지는 합리적인 기본값으로 진행한다.

## 전체 작업 흐름

### 1. 요청한 앱을 완성한다

- 새 앱을 만들거나 화면과 기능을 크게 바꾸는 요청이면 [앱 구현과 미리보기](references/app-building.md)를 읽는다.
- 현재 프로젝트에서 필요한 파일만 먼저 확인한다. 관련 없는 폴더를 광범위하게 읽지 않는다.
- 기존 실행 방식과 의존성을 함부로 교체하지 않는다.
- 앱의 주요 기능, 오류 상태, 모바일 사용성과 접근성을 요청 범위에 맞게 구현한다.
- 장식용 기능, 불필요한 상태 관리와 요청하지 않은 외부 서비스를 추가하지 않는다.
- 앱에 자체 로그인이 필요하면 플랫폼 로그인과 섞지 않고 앱 기능으로 구현한다.

Node 서버는 `process.env.PORT`를 사용하고 외부에서 접근할 수 있게 listen해야 한다. 구체적인 실행 계약이나 Dockerfile 판단이 필요하면 [배포 계약과 복구](references/deployment-contract.md)를 읽는다.

### 2. 설정과 영속 자원 요구를 정리한다

- 공개해도 되는 일반 설정은 `env`로 분류한다.
- API 키, 비밀번호와 접속 Credential은 `secrets`로 분류한다.
- 비밀값 원문을 소스, 답변, 로그나 검증 요청에 넣지 않는다.
- 검증에는 비밀값 원문 대신 `secretKeys`만 전달한다.
- 앱이 데이터 저장이나 파일 업로드를 요구하면 [DB와 파일 Storage](references/resource-bindings.md)를 읽는다.
- 설정을 추가, 변경하거나 삭제할 때는 [설정과 비밀값](references/configuration-and-secrets.md)을 읽는다.

### 3. 완성된 소스를 검증한다

소스 변경을 마친 뒤 `validate_project`를 호출한다.

- 로컬 작업물은 현재 프로젝트의 절대 경로를 사용한다.
- public Git 저장소는 HTTPS 주소를 사용할 수 있다.
- `deployable`이 `false`면 `issues`의 `path`, `message`, `fix`를 읽고 코드를 수정한다.
- `severity: error`를 모두 해결한 뒤 다시 검증한다.
- 소스를 한 줄이라도 수정했으면 이전 검증 결과를 재사용하지 않고 다시 검증한다.
- warning은 배포를 막지 않는다. 보안, 데이터 손실 또는 주요 기능에 영향을 주는 경우에만 사용자에게 알린다.
- 검증을 우회하거나 분석 결과에서 요청 기능을 제거해 억지로 통과시키지 않는다.

검증이 성공한 뒤에는 배포 전까지 제품 소스를 계획적으로 더 수정하지 않는다. 수정이 필요해지면 다시 검증한다.

### 4. 검증한 소스를 배포한다

`deploy_project`에 검증할 때 사용한 것과 같은 소스를 전달한다.

- 커밋하지 않은 로컬 변경이 있으면 로컬 경로를 사용한다.
- Git 주소를 사용하면 원격 저장소에 올라간 내용만 배포된다.
- 기존 앱을 갱신할 때는 기존 배포 이름을 재사용한다.
- 이름을 생략하면 플러그인이 프로젝트 이름에서 안전한 값을 만든다.
- CPU와 메모리는 사용자가 특별히 요구하거나 기본값으로 부족한 근거가 있을 때만 지정한다.
- 일반 설정은 `env`, 비밀값은 `secrets`로 전달한다.
- 같은 비밀값을 답변이나 후속 도구 호출에 다시 표시하지 않는다.

배포 요청은 빌드, 실행과 healthcheck가 끝날 때까지 기다린다. 성공 응답의 `url`을 사용하고 주소를 이름으로 직접 조립하지 않는다.

### 5. 결과를 전달한다

성공하면 다음 순서로 짧게 답한다.

1. 앱이 준비됐다는 결론
2. 정확한 접속 URL
3. 사용자가 지금 할 수 있는 주요 기능
4. 꼭 알아야 하는 제한이 있을 때만 한 줄 설명

기본 답변에는 내부 ID, revision 번호, 이미지 이름, host port, 토큰, 명령어와 임시 경로를 넣지 않는다.

예시:

> 앱을 배포했습니다: https://example.example.com
>
> 이제 할 일을 추가하고 완료 상태를 관리할 수 있습니다.

## 실패 처리와 재시도

- 실패 응답의 `stage`를 먼저 확인한다.
- build, run 또는 health 실패는 `deployment_logs`로 원인을 확인하고 수정한 뒤 다시 검증한다.
- 원인을 확인하지 않은 동일 배포 반복은 하지 않는다.
- queue 실패는 일시적일 수 있다. 짧게 기다린 뒤 한 번만 다시 시도한다.
- 인증, 권한, 사용량 제한과 접근 오류는 임의로 우회하지 않는다.
- 배포 이름 충돌 외에는 이름을 추측해서 바꾸지 않는다. 기존 URL이 불필요하게 달라질 수 있다.
- 새 revision이 실패해도 이전 revision은 계속 서비스된다. 이전 앱을 중지하거나 삭제하지 않는다.

단계별 원인과 조치 기준은 [배포 계약과 복구](references/deployment-contract.md)를 따른다.

## 연결과 인증

연결이나 인증이 의심되면 `paas_whoami`를 한 번 호출한다.

- Credential이 없으면 현재는 운영자에게 `PAAS_TOKEN`을 받아 설정하도록 안내한다.
- 401이면 Credential이 잘못됐거나 폐기된 것이다. 재발급이 필요하다고 설명한다.
- 연결 실패면 PaaS 주소나 서비스 상태를 확인해야 한다.
- 토큰 원문을 사용자에게 되읽거나 로그에 남기지 않는다.
- 현재는 개인 Workspace가 기본값이다. Team Workspace 선택은 플랫폼이 지원된 뒤 도구 인자로 전달한다.

## 기존 배포 관리

- `list_deployments`: 사용자가 관리할 수 있는 앱 목록과 상태
- `deployment_status`: 현재 상태와 접속 URL
- `deployment_logs`: build 또는 runtime 문제 확인
- `deployment_config`: 일반 설정과 비밀값 키 이름 확인
- `set_deployment_config`: 설정 추가, 변경과 삭제
- `paas_whoami`: 사용자, Workspace와 연결 상태 확인

다른 Workspace의 배포는 존재 여부를 추측하지 않는다. 404면 권한이 없거나 대상이 없는 것으로만 설명한다.

## 현재 플랫폼 범위

- 로컬 프로젝트와 public Git 저장소를 배포할 수 있다.
- 일반 Node 앱, 주요 Node 웹 프레임워크와 자체 Dockerfile을 지원한다.
- 일반 환경변수와 암호화된 비밀값을 지원한다.
- PostgreSQL과 파일 Storage 자동 연결은 아직 구현 중이다.
- private Git 저장소 인증은 아직 지원하지 않는다. 커밋하지 않은 변경이나 private 저장소는 로컬 경로로 배포한다.
- 배포 관리 권한과 배포 앱 내부 사용자 인증은 서로 별개다.
