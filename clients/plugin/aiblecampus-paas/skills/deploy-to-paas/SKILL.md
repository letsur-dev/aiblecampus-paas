# 에이블캠퍼스 PaaS 배포

## 무엇을 하는 스킬인가

사용자가 만든 웹 애플리케이션을 PaaS에 올려 접속 가능한 URL을 받는다. 인프라 설정은 플랫폼이 처리하므로 사용자는 앱 코드만 신경 쓰면 된다.

## 배포 절차

1. **배포 전 검증**: `validate_project` 도구를 먼저 호출한다. 이 도구는 실행 자원을 만들지 않고 프로젝트를 분석한다.

   - `deployable`이 `false`면 `issues`의 `path`, `message`, `fix`를 읽고 프로젝트를 수정한다.
   - `severity`가 `error`인 항목을 모두 해결한 뒤 다시 검증한다.
   - `warning`은 배포를 막지 않지만 사용자에게 알려준다.

   앱은 `process.env.PORT`를 읽어 listen해야 한다. 이것이 플랫폼의 1차 계약이다.

   ```js
   const port = Number(process.env.PORT || 3000);
   server.listen(port, "0.0.0.0");
   ```

   `0.0.0.0`으로 바인딩해야 컨테이너 밖에서 접속된다. `127.0.0.1`로 bind하면 배포는 성공해도 접속이 안 된다.

2. **배포 실행**: 검증 결과의 `deployable`이 `true`일 때 `deploy_project` 도구를 호출한다. `path`에 프로젝트 디렉토리의 절대 경로를 넘긴다. `name`을 생략하면 디렉토리 이름에서 만든다.

   git 저장소를 그대로 배포할 수도 있다. `path`에 public 저장소의 https 주소를 넣으면 서버가 직접 clone한다. 소스를 올리지 않아 큰 저장소에서 빠르다. branch나 tag는 `ref`, monorepo 안의 하위 디렉토리는 `subdir`로 지정한다.

   | 상황 | `path`에 넣는 값 |
   | -- | -- |
   | 지금 작업 중인 코드를 올린다 | 프로젝트 디렉토리의 절대 경로 |
   | 이미 올라간 저장소를 배포한다 | `https://github.com/소유자/저장소` |

   커밋하지 않은 변경을 배포하려면 로컬 경로를 쓴다. git 주소를 주면 저장소에 올라간 내용만 배포된다.

3. **결과 전달**: 응답의 `url`을 사용자에게 그대로 알려준다. 이 URL은 재배포해도 바뀌지 않는다.

## 배포 이름과 접속 주소

- 배포 이름은 사용자별로만 유일하다. 다른 사람이 같은 이름을 써도 서로 영향이 없다.
- 접속 주소의 하위 도메인에는 소유자 이름이 함께 붙는다. `todo`로 배포하면 주소는 `todo-<소유자>` 형태가 된다.
- 응답의 `url`을 그대로 쓴다. 이름으로 주소를 직접 조립하지 않는다.

## 실패했을 때

응답에 실패 단계(`stage`)가 담겨 있다. 단계에 따라 대응이 다르다.

| stage      | 뜻                      | 대응                                                        |
| ---------- | ----------------------- | ----------------------------------------------------------- |
| `fetch`    | 소스를 못 가져옴        | git 주소, `ref`, `subdir`이 맞는지 확인한다. public 저장소여야 한다 |
| `analyze`  | 프로젝트 구조를 못 읽음 | `package.json`이 있는지 확인한다                            |
| `validate` | spec을 만들 수 없음     | 대개 포트 문제다. `process.env.PORT`를 읽도록 코드를 고친다 |
| `build`    | 이미지 빌드 실패        | `deployment_logs`로 build 로그를 읽어 원인을 찾는다         |
| `run`      | 컨테이너 기동 실패      | 실행 명령과 의존성을 확인한다                               |
| `health`   | 응답 없음               | `0.0.0.0` 바인딩과 주입된 `PORT` 사용을 확인한다            |

빌드나 실행이 실패하면 반드시 `deployment_logs`로 로그를 확인한 뒤 코드를 고친다. 원인을 보지 않고 같은 배포를 반복하지 않는다.

## 연결이나 인증이 실패할 때

`paas_whoami`를 먼저 호출해 주소와 토큰 설정을 확인한다.

- **토큰이 없다는 응답**: 사용자에게 운영자로부터 토큰을 받아 `PAAS_TOKEN` 환경변수에 넣으라고 안내한다. 설정 후 Claude Code를 다시 시작해야 한다.
- **401 응답**: 토큰이 폐기됐거나 잘못됐다. 운영자에게 재발급을 요청하라고 안내한다.
- **연결 실패**: `PAAS_API_URL`이 올바른지, 플랫폼이 기동 중인지 확인하라고 안내한다.

토큰 값 자체를 사용자에게 되읽어 주거나 로그에 남기지 않는다.

## 상태와 로그 확인

- `validate_project`: 실행 자원을 만들지 않는 배포 전 판정과 수정 지침
- `paas_whoami`: 접속 주소와 인증된 소유자
- `deployment_status`: 현재 상태, 접속 URL, revision 번호
- `deployment_logs`: `type`을 `build`나 `runtime`으로 지정한다
- `list_deployments`: 내가 올린 배포 목록

## 알아둘 것

- 재배포하면 새 revision이 만들어지고, healthcheck를 통과해야 교체된다. 새 버전이 뜨지 않으면 이전 버전이 계속 서비스된다.
- 배포 이름은 소문자, 숫자, 하이픈만 쓴다. 소유자 이름까지 합쳐 63자를 넘을 수 없다.
- git 배포는 public 저장소만 된다. private 저장소는 아직 지원하지 않으므로 로컬 경로로 올린다.
- 데이터베이스와 파일 저장소, 비밀값 주입은 아직 지원하지 않는다. 요청하면 배포가 거부된다.
- 다른 사람의 배포는 조회도 삭제도 되지 않는다.
